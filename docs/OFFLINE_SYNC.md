# Workshop application: offline and synchronisation

The workshop application is the `/m` area of the Angular project, installable as a PWA. An operator creates lots,
scans labels, stores lots and loads pickups with large touch targets (64 px, keypad for the weight, no dense table).

## What works without network

| Action | Offline | Why |
|---|---|---|
| Create a lot (M2-01) | Yes | Recorded on the device, sent later |
| Store a lot | Yes | Same path |
| Open a lot by scanning | No | The lot is read from the server |
| Load a pickup (M4-04) | No | It commits the pickup towards the provider; both sides must see the same state |
| Print a label | No | The PDF is generated by the server once the lot has its number |

The application shell itself is cached by the service worker (production build), so it opens without network once it has
been opened online.

## Principle

Every workshop action takes the same path, online or not: **written to IndexedDB first, then pushed**. Nothing depends on
the network being there at the moment of the action, so there is nothing to lose when it drops.

```
operator ──▶ Offline.createLot() ──▶ IndexedDB "operations" (status pending)
                                         │  online event / app start / manual "Synchroniser"
                                         ▼
                             POST /api/v1/sync/push   (device bearer token, no cookie)
                                         ▼
                      per operation: applied │ rejected │ conflict │ retry
```

Client: `frontend/src/app/core/offline/offline.ts` (Dexie database `divawaste-workshop`, tables `operations` and `meta`).
Server: `app/Modules/Sync` (`ApplyOfflineOperations`, table `sync_operations`).

## Protocol

1. **Device registration** — `POST mobile/devices` (cookie session) returns a device token. One device belongs to one
   user of one company; another user signing in on the same tablet gets a new token.
2. **Reference data** — `GET sync/bootstrap` returns the sites and zones where the user may create lots and the active
   waste types. Cached on the device and refreshed at each start.
3. **Push** — `POST sync/push` with up to 100 operations:

   ```json
   { "sent_at": "…", "operations": [
     { "id": "01J…", "sequence": 12, "type": "lot.create", "occurred_at": "…",
       "payload": { "ulid": "01J…", "site": "…", "zone": "…", "waste_type": "…", "net_weight_kg": "42.5" } } ] }
   ```

   The answer gives, per operation id, `applied` (with the lot number), `rejected` (validation or authorisation — the
   reason is returned), `conflict` (the lot changed meanwhile) or `retry` (unexpected server failure).

## Guarantees

- **No duplicate.** The operation id is generated on the device and stored in `sync_operations`: a replay returns the
  first outcome instead of acting twice. The lot ULID is also generated on the device, so even a new operation for the
  same lot cannot create a second lot.
- **No loss.** An operation leaves the queue only when the server has answered for it. A dropped connection marks
  nothing: everything is sent again. Rejected and conflicting operations stay on the device, visible in
  "File de synchronisation" with the reason, until the operator retries or discards them.
- **Order.** Operations are sent in the order they were recorded (`sequence`).
- **Authorisation is checked at synchronisation**, with the rights the user has then, on the site of each operation.
- **Expired session.** Synchronisation uses the device token, not the web session. If the token is revoked the queue is
  kept and the operator is asked to sign in again.
- The date kept for the lot is when it was recorded on the device (`occurred_at`), not when it was synchronised.

`sync/push` is exempt from CSRF verification because it is called without cookies; it accepts device tokens only.

## Scanning

`QrScannerComponent` uses ZXing on the rear camera. The label carries the lot's tag value; `GET lots/scan/{tag}` is an
indexed lookup. When the camera is refused or absent, the code printed under the QR can be typed — a scan is never a
dead end.

## Verified, and not

- Verified in a phone-sized headless browser against the real API: lot created online; network cut; lot created and
  shown as pending; network restored; lot numbered without user action; pickup loaded by entering the label codes.
- Verified by backend tests (`OfflineSyncTest`): replay, rejection, conflict, authorisation, tenant isolation.
- **Not verified**: a real phone or tablet, the camera decoder on real labels, use with gloves, iOS installation
  (a PNG home-screen icon is missing), several days of offline queue.
